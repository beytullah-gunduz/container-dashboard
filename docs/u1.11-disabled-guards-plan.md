# U1.11 — `enabled = false` is not a safety boundary (disabled-control guards)

**Audit story:** `docs/ux-audit/ux-1-destructive-actions-and-feedback.md` → U1.11 (P1, platform).
**Branch:** `feature/u1.11-disabled-guards`, based on `main` after the U1.4 merge.

## The problem

Compose Multiplatform 1.12.0 registers the `OnClick` semantics action on every
`clickable` regardless of `enabled`, and the desktop accessibility bridge invokes it
without consulting `SemanticsProperties.Disabled`. Any accessibility client — VoiceOver,
Accessibility Inspector, macOS automation — can therefore press a *disabled* button and
run its handler.

Observed live during the U1.4 smoke: an AXPress on the disabled typed-count **Delete**
button ran `onConfirm` and removed every container in the list without the count ever
being typed.

U1.4 patched its own two controls. This change fixes the rest of the blast radius the
audit recorded, and closes the **re-entrancy** hole behind it: even without an
accessibility client, every bulk operation in the app can be fired twice because its
`isRunning` flag is only raised *inside* the coroutine it launches.

## Root cause, with evidence

1. **Bulk operations set their busy flag inside `viewModelScope.launch`, not at the call.**
   `ContainersScreenViewModel.kt:165-180` (`stopSelectedContainers`), `:182-205`
   (`deleteSelectedContainers`), `:208-230` (`deleteAllContainers`) and
   `ListScreenViewModel.kt:112-127` (`deleteSelected`, shared by Images / Volumes /
   Networks) all begin `viewModelScope.launch { _isX.value = true; … }`. A second call —
   a double-press, or an AX press on the disabled button — enters the same path and
   launches a duplicate pass over the same ids.
2. **Neither resets the flag on failure.** `_isX.value = false` sits on the happy path
   only; if `repo.refreshContainers()` throws, or the scope is cancelled mid-pass, the
   flag stays `true` and the control is disabled for the rest of the session.
3. **The engine Restart button is two racing coroutines.** `SettingsScreen.kt:718-726`
   calls `onStop()` then `onStart(...)`; those map to
   `SettingsScreenViewModel.stopEngine()` (`:117-123`) and `startEngine()` (`:103-115`),
   each of which opens its **own** `viewModelScope.launch`. The second does not wait for
   the first, so `colima stop` and `colima start` are dispatched concurrently.
   `EngineManager.startEngine`/`stopEngine` (`EngineManager.kt:104,151`) have no
   mutual-exclusion of any kind, and each begins with `_output.value = ""`, so the two
   also fight over the command-output buffer.
4. **Three controls have an immediate irreversible handler and nothing behind them.**
   `CompactCheckbox` (`CompactCheckbox.kt:54`) calls `onCheckedChange` from inside
   `clickable(enabled = enabled)`; the system-network row trash
   (`NetworksScreen.kt:794-798`) calls `onRemove` directly; the network context menu's
   Delete item (`NetworkContextMenu.kt:52-66`) calls `onRemove()` behind `enabled = canDelete`.

## Design decisions (fixed — do not relitigate)

- **D1 — the ViewModel is the safety boundary for bulk operations.** Each guarded method
  checks its busy flag, snapshots its input, and raises the flag **synchronously, before**
  `viewModelScope.launch`; the reset moves into a `finally`. A re-entrant call returns
  immediately. This covers both button variants (compact + expanded) of every bulk control
  with one edit each, and it is unit-testable without any UI. (Known and accepted: if
  `viewModelScope` is already cancelled the launched body never runs, so the `finally`
  never fires and the flag stays raised — but that happens only after `onCleared()`, when
  the ViewModel and its flags are unobservable. There is no suspension point and no
  throwing statement between the flag-raise and the `launch`, so nothing else can strand
  it.)
- **D2 — handlers additionally re-check the precondition where a press has a visible
  effect before reaching the ViewModel.** An AX press on a disabled *Delete N selected*
  button would otherwise still open the confirmation dialog (the deletion would then be
  swallowed by D1 — safe, but silently confusing). The re-check is the same one-token
  idiom U1.4 already uses (`onClick = { if (cond) act() }`,
  `DeleteAllContainersDialog.kt:103`). Do **not** invent a helper function or wrapper
  component; match the existing idiom.
- **D3 — engine operations are serialized by one lock that rejects rather than queues,**
  and Restart becomes a single operation end-to-end. `EngineManager` gets a `Mutex` taken
  with `tryLock()`: a second concurrent start/stop/restart returns `false` immediately
  and does not touch `_actionState` or `_output`. A new `EngineManager.restartEngine`
  holds that lock once and runs stop-then-start in order, sharing one output buffer.
  **If the stop leg fails, the restart aborts and the failure stands as the reported
  state — start is not attempted.** Rationale: starting on top of a failed stop produces
  a state neither the user nor the app can reason about; the user sees the stop error and
  can retry. The reachable failure is the 60 s `TIMEOUT_STOP_SECONDS`
  (`EngineManager.kt:49`): a slow stop is force-killed and reports failure, and Restart
  then aborts having half-stopped the VM. That is the intended trade — the user sees the
  stop error rather than a start racing a dying VM.
- **D4 — the bridge itself is not patched here.** Overriding or stripping `OnClick`
  semantics on disabled nodes would be a guess about Compose internals and would
  compromise the accessibility labels U4.1 just enabled. The upstream report to JetBrains
  is tracked in the audit entry, not in this change.
- **D5 — `enabled =` expressions and all visual states stay exactly as they are.** This
  change adds guards; it does not re-style, re-enable, or disable anything.

     * Stops the engine and starts it again as ONE operation (UX audit U1.11).
     * Previously the Settings screen fired `stopEngine()` and `startEngine()` as two
     * independent coroutines, so `colima stop` and `colima start` ran concurrently and
     * fought over [output]. Holding [operationLock] across both legs also makes a
     * second Restart press a no-op while the first is still running.
     *
     * A failed stop aborts the restart: the failure state stands and no start is
     * attempted, because starting on top of a half-stopped VM produces a state neither
     * the user nor the app can reason about.
     */
    suspend fun restartEngine(
        type: EngineType,
        profile: String? = null,
        cpu: Int? = null,
        memory: Int? = null,
        disk: Int? = null,
    ): Boolean {
        if (!operationLock.tryLock()) {
            logger.warn("Ignoring restart request: another engine operation is already running")
            return false
        }
        return try {
            _output.value = ""
            if (!stopEngineLocked(type, profile)) {
                false
            } else {
                startEngineLocked(type, profile, cpu, memory, disk)
            }
        } finally {
            operationLock.unlock()
        }
    }
