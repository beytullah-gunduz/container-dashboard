## G1 — Files tab crashes the window on duplicate LazyColumn keys when a symlinked directory is expanded

- **Severity:** High · **Effort:** M
- **Verified by:** main (code). The crash itself is inferred from the code path plus Compose's duplicate-key check; nothing was run at review time.
- **Status:** fixed after this baseline: rows are keyed by a new `FileTreeNode.treePath` (position in the tree), and the tree's expanded/loading/error maps use it; `entry.path` stays the real path for read and download. Reproduced first by a headless Compose UI test and in the running app under hot reload (fake engine with a merged-/usr layout); with the key reverted both show `Key "/usr/bin/ls" was already used`. Anchors below are the pre-fix code at `c813407`.
- **Files:** `commonMain/ui/components/FilesTabContent.kt:186` (`items(state.nodes, key = { it.entry.path })`); `commonMain/ui/screens/viewmodel/AppViewModel.kt:257-271` (`TreeState` keyed by entry path), `:295-313` (`toggleNode`), `:401-436` (`loadChildren` lists `resolveListPath(entry)` and stores the result under `entry.path`), `:438-449` (`resolveListPath` returns the symlink target), `:457-483` (`flattenTree` emits both subtrees); `desktopMain/data/repository/DesktopDockerRepository.kt:558-585` (`listContainerDirectory`; `parseLsOutput(stdout, normalized)` at `:574` — `normalized` is the requested path, i.e. the target); `commonMain/data/util/ContainerFileParsing.kt:52` (`path = joinPath(basePath, name)`); pin test `commonTest/AppViewModelFileBrowserTest.kt:357-380` asserts that `/bin`'s child carries `/usr/bin/ls`.

**Problem.** A symlink-to-directory is expandable (`FileType.SYMLINK`), but its children are
parsed with the target directory as `basePath`, so they get exactly the same `path` values as the
real directory's children. `flattenTree` emits both subtrees and the LazyColumn keys rows by
`entry.path`. Compose throws `IllegalArgumentException: Key "…" was already used` when two items
with one key are composed, and the project's own comment (`desktopMain/terminal/JediTermConsole.kt:116-121`)
records what an uncaught composition throwable does here: a bare "Unknown error" dialog and the
window is torn down. Side effect: `expandedPaths`, `loadingPaths` and `nodeErrors` use the same
key, so expanding a directory under one copy expands it under the other.

**Failure scenario.** Any merged-`/usr` image (Debian 12+, Ubuntu 22.04+): `/bin -> usr/bin`.
Open the Files tab, expand `/bin`, then expand `/usr` → `/usr/bin`. Both subtrees contain
`/usr/bin/ls`, `/usr/bin/sh`, … and as soon as both are in the viewport the keys collide and the
window goes. Single-expand variants: `/usr/bin/X11 -> .` duplicates its own parent listing; any two
symlinks to one target.

**Fix:** key rows and the tree maps (`childrenByPath`, `expandedPaths`, `loadingPaths`,
`nodeErrors`) by position in the tree (parent's position + own name) instead of by `entry.path`;
keep `entry.path` as the real path, which read and download use.

**Acceptance:** with `/bin -> usr/bin` and `/usr/bin` both expanded, the Files tab composes
without throwing and shows both subtrees; expanding a directory under one copy leaves the other
collapsed; opening a file below the symlink still reads the real path. Pinned by a view-model
test (every visible row has a unique key; separate expanded state under the link) and by a
headless Compose UI test of `FilesTabContent` that fails with the key reverted. `c813407` has no
Compose UI test dependency; the G1 fix adds one (test only).

**Related story:** U5.4 (Files tab) mentions symlink *sorting* only; the crash is not recorded.

## B3 — A failed container-list call is reported as an empty list; the app reacts as if every container was deleted

- **Severity:** Medium · **Effort:** M
- **Verified by:** main (code).
- **Status:** fixed after this baseline: a list call that fails after that list has loaded emits nothing, so subscribers keep the last list, and the first failure of a streak is reported once through `DockerRepository.listRefreshFailures()`, shown as an error snackbar while connected. A failure before the first success still emits an empty list. Applies to all four lists. Pinned by `DesktopDockerRepositoryListRefreshTest` (real repository, in-process engine) and `AppViewModelErrorTest`; the result audit's probe also checked recovery, a real empty list, and a shared-flow restart with a failing first call. Not checked against a real engine.
- **Files:** `desktopMain/data/repository/DesktopDockerRepository.kt:388-400` (poll/event path: any exception → `emptyList()`), `:401-415` (`onStart` path, same), `:416-419` (`catch` → `emptyList()`); `commonMain/ui/screens/viewmodel/AppViewModel.kt:95-100` (`allGone` → cancel follow, reset the logs *and* files panes), `:101-115` (partial-miss branch; not reached by a failed call, an empty list makes `allGone` true); `commonMain/ui/screens/viewmodel/ContainersScreenViewModel.kt:55-58` (`hasLoaded` stays `true`, so the screen renders "No containers", not a loading or error state); `desktopMain/data/repository/DesktopDockerRepository.kt:1274-1285` (running set → `statsManager.retain(emptySet())`) and `commonMain/data/repository/ContainerStatsManager.kt:44-46` (empty running set → `emptyMap()`).
- **Re-anchor note:** the same empty-on-failure pattern is in the images, volumes and networks flows (`imagesShared` `DesktopDockerRepository.kt:934-976`, `volumesShared` `:1043-1103`, `networksShared` `:1165-1205`). Their consumers are less destructive; fix them with the same change.

**Problem.** The list flows have no error channel: failure and "zero containers" are the same
emission, and every consumer treats it as truth. `AppViewModel` destroys the open logs/files pane
and cancels the follow job; the Containers screen shows "No containers"; Monitoring and the tray
report nothing running; the stats cache is pruned. The next successful poll (≤ 15 s, or the next
event) restores the list, but the pane and the follow are gone and the selection may reference ids
the user cannot see.

**Failure scenario.** One `listContainersCmd().exec()` throws for any reason other than "pool shut
down" — a 45 s `responseTimeout` on a busy daemon, a socket hiccup, a retry that itself fails during
a client rebuild (B4) — while the user tails a container's logs. The pane closes by itself, the
follow stops, Containers shows "No containers", the tray says 0 running. Nothing is logged above
WARN and no UI error appears. How often the trigger fires on a healthy local socket is not known
from code; the path itself is unconditional.

**Fix:** do not emit on failure (`runCatching { … }.getOrNull()` + `mapNotNull`, so consumers keep
the last good list) and route the failure to a separate error / `UiMessages` signal. Independently,
make `AppViewModel`'s `allGone` branch require a *successful* list.

**Acceptance:** with an in-process engine (the `DesktopDockerRepositoryStreamsTest` fixture) whose
`/containers/json` succeeds once and then returns 500, the `getContainers` flow emits no empty list
after the failure and the error signal fires once; a view-model test shows that a failed list leaves
`logsPaneState`, the follow job and the Containers screen state untouched.

## B2 — Log follow silently drops the final lines when the stream ends

- **Severity:** Medium · **Effort:** S
- **Verified by:** main (code).
- **Status:** fixed after this baseline: `conflate()` + `transform { emit; delay(100) }` keeps the rate cap and always delivers the last snapshot. Pinned by `DesktopDockerRepositoryStreamsTest`, which fails with `sample(100)` restored. Not checked live.
- **Files:** `desktopMain/data/repository/DesktopDockerRepository.kt:783` (`.conflate().sample(100).flowOn(Dispatchers.IO)` closing `followContainerLogs`, `:727-783`) and `:856` (same, `followMultipleContainerLogs`, `:785-856`); kotlinx-coroutines 1.11.0 `flow/operators/Delay.kt:269-298` (`sample`, read from the sources jar in the Gradle cache); `commonMain/ui/screens/viewmodel/AppViewModel.kt:207-222` (`collect`, then the "--- Stream ended ---" append at `:217-222`).
- **Effect of `9f45245`: B2 is live since that commit.** Before it, a bare `close()` inside the `ResultCallback.Adapter` resolved to the callback's own `Closeable.close()`, not the flow's channel, so a stream the daemon ended never completed the `callbackFlow` — it stayed suspended in `awaitClose`. While its upstream is open, `sample` keeps ticking, so the pending last value was still emitted on the next tick: the tail-drop on completion was not reachable. After it, `onComplete` calls `this@callbackFlow.close()` (`:760`, `:817`), the follow flow completes, and `sample` drops a value that arrived after its last tick. Verified here from the code: `sample`'s completion branch sets `lastValue = DONE` and exits without emitting (`Delay.kt:281-286`), and the operator's own KDoc says the latest element is not emitted if it misses the sampling window. I reach the same conclusion as the report.
- **Version caveat gone:** the report read the 1.11.0 and 1.9.0 sources because the project pinned 1.10.2; `70d3c44` pins 1.11.0, the exact artifact read.

**Problem.** `sample()` holds the latest upstream value in `lastValue` and emits it only on the
next tick. When upstream completes, the `onFailure` branch overwrites `lastValue = DONE` and
exits, so a value received after the last tick is never emitted. Each emission here is a
*cumulative* snapshot, so the lines that arrived in the last ≤ 100 ms before the daemon closed the
follow stream are lost. The view model then appends "--- Stream ended ---" to the previous
snapshot.

**Failure scenario.** A container panics, prints its stack trace and exits; the daemon closes the
follow stream within milliseconds of the last write. The pane shows the logs up to the previous
100 ms tick, then "--- Stream ended ---": the stack trace, the lines the user opened the pane for,
is missing. A one-shot fetch after reopening the pane does show them, so the discrepancy looks like
a bug in the follow.

**Fix:** replace `sample(100)` with a throttle that flushes the last element —
`.conflate().onEach { delay(100) }` is the usual shape — or, on normal completion in
`startFollowing`, re-fetch the tail via `getContainerLogs` before appending the end marker.

**Acceptance:** extend `desktopTest/DesktopDockerRepositoryStreamsTest.kt`: the in-process engine
writes one stdout frame and ends the stream (as its log fixture already does); collecting
`followContainerLogs(...)` into a list must contain a snapshot with that line, and the same for
`followMultipleContainerLogs`. The existing tests only `collect {}` to assert that the flow ends, so
they pass whether or not the frame is delivered; by reading, the new assertion should fail on
`c813407` (not run).

**Note from reading `9f45245` (not a reviewer finding):** the single-container follow now ends
normally on a stream *error* too (`onError` closes without the cause, `:756`), so a failed stream
reads as "--- Stream ended ---" rather than the pane's error state; the group follow forwards the
cause (`:813`).

## B8 — Connection-pool ceiling vs. one persistent stats stream per running container

- **Severity:** Low · **Effort:** M
- **Verified by:** reviewer only (plausible; not verified at runtime).
- **Status:** confirmed by reading docker-java 3.7.1 (`maxConnections(100)` sets both the total and the per-route limit; no connection-request timeout, so httpclient5's 3-minute default applies). **Not fixed: needs a design decision** — a separate HTTP client for long-lived streams (events, stats, log follows), streaming stats only for visible containers (the tray's aggregate needs all running ones), or a larger pool with a short lease timeout.
- **Files:** `desktopMain/data/repository/DesktopDockerRepository.kt:78-91` (`maxConnections(100)` at `:82`; docker-java 3.7.1 applies it as both max-total and per-route, re-checked in the `ApacheDockerHttpClientImpl` bytecode; only `responseTimeout` is set, no connection-request timeout), `:1274-1285` + `commonMain/data/repository/ContainerStatsManager.kt:84-109` (one long-lived `statsCmd` connection per running id, ref-counted), `desktopMain/Main.kt:134-149` (the tray keeps the aggregate subscribed from startup).
- **Effect of `9f45245`:** a stats stream the engine ends normally now completes its flow (`DesktopDockerRepository.kt:1344-1347`); that changes stream lifetime, not the pool-ceiling argument.

**Problem.** Each running container pins one pooled connection; events, log follows and exec sessions
pin more. Around ~95 running containers every one-shot command (list, inspect, start/stop) would block
waiting for a free connection; the wait is bounded only by HttpClient5's default, as no
connection-request timeout is set. Not verified at runtime, and not an issue at the container counts the
UX audit describes.

**Fix:** cap concurrent stats streams (stream only for visible or expanded ids plus the tray's aggregate
at a lower cadence), or raise the pool and set an explicit connection-request timeout.

**Acceptance:** with more running fake containers than the pool size, one-shot calls (list, inspect,
start) still complete within the configured connection-request timeout while stats streams are active.
